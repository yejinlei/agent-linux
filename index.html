原理 结构体 函数

总览：原理-代码映射论

核心信念：内核的每一条设计原理，都能在代码中找到精确的物化载体。不存在"无法落地的原理"，也不存在"没有原理的代码"。每一个指针、每一个链表、每一个回调函数，都是本体论原理的实体化。
原理 P0：内核用 C 语言实现了面向对象

C 语言本身没有类、继承、虚函数。但 Linux 通过「结构体嵌套 + 函数指针表」实现了多态：
• 抽象基类 = 含函数指针表的结构体
• 子类继承 = 嵌入基类结构体作为第一个成员
• 虚函数调用 = 通过函数指针间接调用
• RTTI = 通过 container_of 反解出子类

代码 C0：以 file_operations 为例 include/linux/fs.h:2092
// 抽象"文件操作"基类——多态的函数指针表
struct file_operations {
    loff_t (*llseek) (struct file *, loff_t, int);
    ssize_t (*read) (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write) (struct file *, const char __user *, size_t, loff_t *);
    int (*open) (struct inode *, struct file *);
    int (*mmap) (struct file *, struct vm_area_struct *);
    // … ext4/ext2/proc/tmpfs 各自赋值这些指针，实现多态
};
// 调用时：file->f_op->read(...) 就是"虚函数"调用
原理 P1：container_of —— C 语言的"继承反解"

当一个结构体作为另一个结构体的第一个成员时，它的地址就是宿主的地址。container_of 通过"基类成员指针"反推出"派生类结构体"首地址，等价于 C++ 的 static_cast。

代码 C1：container_of 宏 include/linux/kernel.h:866
/**
 * container_of - 通过成员地址反推结构体首地址
 * @ptr:    成员指针
 * @type:   宿主结构体类型
 * @member: 成员名
 *
 * 原理：结构体起始地址 = 成员地址 - 成员在结构体内的偏移
 */
#define container_of(ptr, type, member) ({ \
    void *__mptr = (void *)(ptr); \
    ((type *)(__mptr - offsetof(type, member))); })

原理 P2：一切皆链表（list_head）

内核不搞侵入式链表，而是让 list_head 作为成员嵌入任何结构。用同一套 list_add/list_del/list_for_each 宏遍历所有对象——进程、文件、inode、设备、定时器…… 这是"多态容器"的极简实现。

    struct list_head *next, *prev;
};

static inline void __list_add(struct list_head *new,
                              struct list_head *prev,
                              struct list_head *next) {
    next->prev = new;
    new->next = next;
    new->prev = prev;
    prev->next = new;
}

第一章 · 进程管理

本体论核心：进程是资源分配的单位，线程是调度执行的单位。在 Linux 里二者合一——线程只是"和别人共享地址空间的进程"。所有运行实体都由 struct task_struct 这一单一数据结构描述，这是整个内核"最肥胖也是最重要的结构体"。

1.1 task_struct：进程本体的数据化身

原理 P3：一个进程 = 一个 task_struct

PCB（进程控制块）在 Linux 中具体化为 task_struct。它聚合了进程的全部属性：
• 身份：pid、uid/gid、creds
• 调度：state、policy、prio、se
• 地址空间：mm（内核线程 mm=NULL）
• 文件系统：fs、files
• 信号：sighand、signal、blocked
• 关系：real_parent、children、sibling
• 关系链表：tasks（链接所有进程）

1.2 进程创建：fork 复制本体

原理 P5：fork 的哲学——"复制但不立即复制"

fork 创建新进程的本体论：父=子在"诞生瞬间"完全相同，随后各自通过 exec 或写内存走向不同命运。
• 传统 fork 是全拷贝，开销大
• Linux 用「写时复制 COW」优化：页表先共享，写时才复制物理页
• clone 比 fork 更灵活：可精确选择共享哪些资源（fs/files/sighand/mm...）
• vfork：连页表都不复制，直接阻塞父进程，子进程必须马上 exec

代码 C5：fork/vfork/clone 统一入口 kernel/fork.c:2653
// 三个系统调用最终都调 _do_fork
SYSCALL_DEFINE0(fork)   { return _do_fork(SIGCHLD, 0, 0, NULL, NULL, 0); }
SYSCALL_DEFINE0(vfork)  { return _do_fork(CLONE_VFORK|CLONE_VM|SIGCHLD, 0, 0, NULL, NULL, 0); }
SYSCALL_DEFINE5(clone, ...) { return _do_fork(clone_flags, newsp, 0, parent_tidptr, child_tidptr, tls); }

// 核心链路：copy_process → dup_task_struct → copy_* → wake_up_new_task
static __latent_entropy struct task_struct *copy_process(...)
{
    struct task_struct *p;
    p = dup_task_struct(current, node);     // 1. 复制 task_struct + 内核栈
    copy_creds(p, clone_flags);            // 2. 复制凭证
    copy_semundo(clone_flags, p);
    copy_files(clone_flags, p);            // 3. 文件描述符表
    copy_fs(clone_flags, p);               // 4. fs(cwd/root)
    copy_sighand(clone_flags, p);          // 5. 信号处理器
    copy_signal(clone_flags, p);
    copy_mm(clone_flags, p);               // 6. 地址空间（COW 就在这里设置）
    copy_thread(clone_flags, sp, arg, p);  // 7. 设置寄存器上下文
    return p;
}
原理 P6：写时复制（COW）的落地

copy_mm 中，子进程页表项与父进程共享物理页，但都标记为"只读"。当任一进程写该页时触发 page fault，缺页处理中才真正分配新物理页并复制——这就是 dup 之后"看似分开、实际共享"的物理意义。

代码 C6：COW 缺页处理 mm/memory.c:2984 (do_wp_page)
static vm_fault_t do_wp_page(struct vm_fault *vmf)
{
    struct page *old_page = vmf->page;
    struct page *new_page;

    // 如果旧页面引用计数 == 1，说明只有我在用，直接把只读变可写（无需复制）
    if (page_count(old_page) == 1) {
        wp_page_reuse(vmf);
        return 0;
    }

    // 引用计数 >1，说明还有别人共享：必须分配新页复制旧内容
    new_page = alloc_page_vma(GFP_HIGHUSER_MOVABLE, vmf->vma, vmf->address);
    cow_user_page(new_page, vmf->address, vma, old_page); // 真正复制 4KB 数据
    wp_page_copy(vmf, new_page);     // 让我的页表指向新页，并设为可写
    return 0;
}

1.3 调度：CFS 完全公平调度

原理 P7：CFS 的理想——每个进程"完美均分"CPU

传统调度用"时间片轮转"，但固定时间片对交互体验不友好。CFS 思路：
• 维护一棵按 vruntime（虚拟运行时间）排序的红黑树
• 每次选择 vruntime 最小的进程运行（即"最受亏待的那个"）
• nice 值决定"权重"：权重越高，真实时间推进 vruntime 越慢——占 CPU 越久
• 调度周期 target_latency（默认 6ms 起步）内所有可运行进程至少轮一次

代码 C7：调度实体 sched_entity include/linux/sched.h:512
struct sched_entity {
    struct rb_node    run_node;       // 红黑树节点（挂入 cfs_rq）
    struct list_head  group_node;
    u64               vruntime;       // ⭐ 虚拟运行时间：CFS 选谁就看这个
    u64               exec_start;     // 本次开始运行时刻
    u64               sum_exec_runtime;// 累计真实运行时间
    u64               prev_sum_exec_runtime;
    u64               vruntime_relative;
    struct sched_avg  avg;            // PELT 负载统计
};
原理 P8：调度类的多态——调度器也能"插拔"

stop → dl（Deadline）→ rt（Real Time）→ cfs（Fair）→ idle，这是调度优先级链。每个类用 sched_class 函数指针表实现自己的 enqueue/dequeue/pick_next_task，主调度器按优先级依次调用——又是 P0 的多态模式。

代码 C8：调度类多态表 include/linux/sched.h:802

    const struct sched_class *next; // 指向下一个优先级更低的调度类

    void (*enqueue_task) (struct rq *rq, struct task_struct *p, int flags);
    void (*dequeue_task) (struct rq *rq, struct task_struct *p, int flags);
    struct task_struct *(*pick_next_task) (struct rq *rq);
    void (*task_tick)     (struct rq *rq, struct task_struct *p, int queued);

    // CFS 实例：fair_sched_class（kernel/sched/fair.c）
    // RT 实例：rt_sched_class（kernel/sched/rt.c）

};

// 主调度器按优先级链遍历：
for (class = sched_class_highest; class; class = class->next) {
    p = class->pick_next_task(rq);
    if (p) return p;  // 高优先级类有进程就用它
}
原理 P9：上下文切换 = 换 mm + 换寄存器

"切换进程"本质就是两件事：① 切换页表（switch_mm，从而切换虚拟地址空间）；② 切换内核栈与寄存器（switch_to 汇编）。进程切换的代价主要来自切换页表导致 TLB 刷掉。

代码 C9：context_switch kernel/sched/core.c:3569
static __always_inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
             struct task_struct *next)
{
    mm_switch(mm, prev->active_mm, next->mm);
    // 1. 切换地址空间
    if (!next->mm) {     // 内核线程：不换，借用prev的 mm
        next->active_mm = prev->active_mm;
    } else {             // 用户进程：真正切换页表
        switch_mm_irqs_off(prev->active_mm, next->mm, next);
    }

    // 2. 切换寄存器上下文与栈（最后一步，不会返回）
    switch_to(prev, next, prev);
    return finish_task_switch(prev);
}

第二章 · 内存管理

本体论核心：内存管理是"地址→物理页帧"的映射游戏。进程看到的是平坦的虚拟地址空间，内核通过页表将其拆分、映射、保护、按需分配。核心对象是 mm_struct（进程视角）和 page（物理页帧视角）。

2.1 mm_struct：进程的地址空间本体

原理 P10：进程 = 一段"虚拟地址空间"

每个进程"独占"0~248-1（x86_64 用户态）的虚拟地址，这是 mm_struct 描述的：
• pgd：页全局目录基址（写入 CR3 寄存器）
• mmap：VMA 链表头，描述已分配的各个区间
• mm_rb：同一组 VMA 的红黑树（加速查找）
• 起始/结束地址：mmap_base、start_brk（堆）、start_stack（栈）

代码 C10：mm_struct 结构 include/linux/mm_types.h:482

原理 P11：VMA——连续虚拟区间的抽象

虚拟地址不是一整块分配，而是按 VMA（Virtual Memory Area，虚存区）一段段切分：代码段、数据段、堆、栈、每个 mmap 的文件/匿名区各是一个 VMA。每个 VMA 记录权限（rwx）和关联的文件/匿名。
malloc 本质上只在堆顶 brk 或 mmap 新建 VMA，并不真的分配物理页——物理页在第一次读/写这个地址时由缺页异常"按需分配"。

2.2 缺页异常（Page Fault）：按需分配的实现

原理 P12：不访问就不分配 —— 虚拟内存的灵魂

用户 malloc(1G) 后，内核只是创建了一个 VMA，没有分配任何物理页。等进程第一次读/写这个地址，MMU 查页表发现页表项为空，抛出 #PF（Page Fault）异常，陷入内核，内核才真正 alloc_page 并填页表。
缺页处理分三种：
① 匿名缺页 → 分配新物理页、清零、建立映射
② 文件缺页 → 从磁盘读文件到 page cache 再映射
③ 写时复制（COW 已在 C6 中讨论）→ 复制写

代码 C12：x86 缺页异常入口 arch/x86/mm/fault.c:1254 do_page_fault
// CPU 自动压入错误码 error_code
// error_code 低 3 位：
//   bit0: 0=页不存在 1=权限违例
//   bit1: 0=读 1=写
//   bit2: 0=内核态 1=用户态
dotraplinkage void do_page_fault(struct pt_regs *regs, unsigned long error_code)
{
    struct vm_area_struct *vma;
    unsigned long address = read_cr2(); // CR2=触发缺页的虚拟地址
    struct task_struct *tsk = current;
    struct mm_struct *mm = tsk->mm;

    vma = find_vma(mm, address);       // 在 mm_rb 红黑树中找 VMA
    if (!vma || address < vma->vm_start)
        goto bad_area;                   // 野指针 → SIGSEGV

    if (!(vma->vm_flags & (error_code & PF_WRITE ? VM_WRITE :
                            (error_code & PF_INSTR ? VM_EXEC : VM_READ))))
        goto bad_area;                   // 权限违例 → SIGSEGV

    handle_mm_fault(vma, address, flags); // 真正处理
}
原理 P13：find_vma 的红黑树查找

给定虚拟地址 addr，找第一个 vm_end > addr 的 VMA；若 vma->vm_start ≤ addr 则命中，否则没分配。这是所有内存操作（读/写/mmap/munmap）的基础查询，所以用红黑树而非链表，O(log n)。

代码 C13：find_vma 主循环 mm/mmap.c:2337
struct vm_area_struct *find_vma(struct mm_struct *mm, unsigned long addr)
{
    struct rb_node *rb_node;
    struct vm_area_struct *vma = NULL;

    rb_node = mm->mm_rb.rb_node;
    while (rb_node) {
        vma = rb_entry(rb_node, struct vm_area_struct, vm_rb);
        if (vma->vm_end > addr) {       // 候选：结束>addr
            if (vma->vm_start <= addr)    // 起始<=addr → 命中！
                break;
            rb_node = rb_node->rb_left;   // 太大了，往左走
        } else {
            rb_node = rb_node->rb_right;  // 太小了，往右走
            vma = NULL;
        }
    }
    return vma;
}

2.3 四级页表：地址翻译的本质

原理 P14：为什么要多级页表？

x86_64 用户地址 48 位。若用单级页表，一个进程需 248/212 = 236 ≈ 680 亿条页表项，根本放不下。
四级页表把虚拟地址切成 5 段：
| PGD(9) | PUD(9) | PMD(9) | PTE(9) | offset(12) |
每级 9 位 = 512 项（正好占一页 4KB），缺了上一级就不用建下一级——稀疏映射的完美解决方案。

第三章 · 中断与异常

本体论核心：中断是"外部世界打断 CPU 的本体"。硬件通过 IDT 找到入口，内核分"上半部"（关中断、短小、快速应答）和"下半部"（开中断、耗时、可延后）处理，以兼顾响应速度与处理深度。

3.1 中断描述符表 IDT：中断号→处理函数的映射表

原理 P15：中断本质是"编号→函数"的间接调用

CPU 用一根 INTR 引脚接收中断，同时通过数据总线接收 8 位向量号（0~255）。CPU 用这个号查 IDT 找到门描述符，得到入口 CS:RIP——跟系统调用、异常完全同构。
• 0~31：处理器异常（除0、缺页 #PF、断点 #BP 等）
• 32~127：外部硬件中断（IRQ0=时钟、IRQ1=键盘…）
• 128（0x80）：传统 int 0x80 系统调用
• 0~255 其他：可用作 MSI、IPI 等

3.2 上半部/下半部：为什么要分两层？

原理 P17：中断"快响应、慢处理"的分层哲学

中断来的时候 CPU 关中断，若处理太久会丢失其他中断，系统卡顿。所以拆成两层：
• 上半部（HardIRQ）：request_irq 注册的 handler，关中断执行，只做"应答+把下半部挂起"等最少工作
• 下半部三种机制，按"延迟要求"由快到慢：
　① softirq（最快，静态预定义 10 种，如 NET_RX/TIMER）
　② tasklet（基于 softirq，动态创建，同类型不可并发）
　③ workqueue（最慢，跑在专用内核进程上，允许睡眠）

原理 P18：spinlock 为什么不能睡眠？

spin_lock 后关闭/保持抢占，若持锁时你 sleep 触发 schedule，下一个进程在同一CPU也想抢这把锁，就会永远旋转——死锁。所以 spinlock 临界区内绝对禁止睡眠、禁止复制用户页（可能触发缺页→IO→睡眠）。

第六章 · 网络协议栈

本体论核心：网络的本体是 sk_buff（套接字缓冲区），它像一个"指针滑动的容器"承载着数据包在各层间流动。收发路径是"层套层"的封装/解封装过程；TCP 用状态机保证可靠性。

6.1 sk_buff：网络数据包的本体

原理 P20：为什么 sk_buff 要那么多指针？

6.3 TCP 三次握手：状态机精确对应代码

原理 P22：三次握手为什么是三次？

核心问题：确认双方"发"和"收"的能力都正常。
• 客户端 SYN → 服务端：证明"客户端能发"
• 服务端 SYN+ACK → 客户端：证明"服务端能收、能发"
• 客户端 ACK → 服务端：证明"客户端能收"
两次不够（服务端无法确认客户端能收）；四次没必要（中间的ACK+SYN可以合并）。
三次握手的过程同时也是内核创建"半连接队列（SYN queue）"和"全连接队列（accept queue）"的过程。

accept() 就是"从 accept queue 拿出一个已经三次握手完成的 sock"，所以 accept 不会等到 SYN，它只取 ESTABLISHED 的连接。

第七章 · 设备驱动模型

本体论核心：Linux 用 bus-device-driver 三角模型实现驱动"自动发现、自动绑定"。驱动与设备通过 id_table match，match 上了就调用 probe 让驱动去初始化设备。所有设备最终以 sysfs 的形式向用户态展现。
原理 P23：kobject —— 设备模型的地基

sysfs 里的每个目录对应一个 kobject：有名字、有父节点、有引用计数、有属性（文件）。bus/device/driver/class 都是"内嵌 kobject"的派生结构——又一次 P0 的 C 语言面向对象。

代码 C23：三大核心结构 include/linux/device.h / include/linux/bus.h
struct bus_type {
    const char       *name;           // "pci"/"usb"/"platform"/"i2c"...
    struct bus_attribute *bus_attrs;
    struct device_attribute *dev_attrs;
    struct driver_attribute *drv_attrs;

    int (*uevent)(...);
    int (*probe)(struct device *dev);

};

struct device_driver {
    const char            *name;
    struct bus_type       *bus;      // 挂载到哪个总线
    const struct of_device_id *of_match_table;  // 设备树匹配表
    const struct acpi_device_id *acpi_match_table;

};

struct device {
    struct kobject         kobj;

};

设备驱动匹配流程

1设备注册：PCI 枚举 / 设备树解析 / ACPI 发现真实硬件后，device_register() 将 device 挂入 bus->p->devices_kset 链表。
2驱动注册：驱动模块加载时 module_init → driver_register()，把 driver 挂入 bus->p->drivers_kset。
3match：无论设备先来还是驱动先来，内核都会调用 bus->match()（如 platform_match 按 name 比对、pci_match 按 vendor:device ID 比对、of_match_table 按 compatible 比对）。
4probe：match 成功后，调用 driver->probe(dev)——这是驱动做一切初始化（分配资源、ioremap、注册中断、注册字符设备、创建设备节点）的地方。
5绑定：probe 返回 0 表示成功，device->driver = driver，二者绑定；之后用户态 open("/dev/xxx") 就能调到 file_operations 里的函数。
// 一个典型 platform_driver 例子（简化）
static const struct of_device_id my_of_match[] = {
    { .compatible = "mycompany,mydev" }, { }
};

static int my_probe(struct platform_device *pdev) {
    struct resource *res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    void __iomem *base = devm_ioremap_resource(&pdev->dev, res);
    devm_request_irq(&pdev->dev, irq, my_irq_handler, 0, "mydev", NULL);
    misc_register(&my_miscdev);  // 注册 /dev/mydev
    return 0;
}

static struct platform_driver my_drv = {
    .probe = my_probe,
    .driver = { .name = "mydev", .of_match_table = my_of_match },
};
module_platform_driver(my_drv);   // module_init/exit 宏

第八章 · 系统调用

本体论核心：系统调用是"用户态向内核态请求服务的唯一合法入口"，本质是"用约定好的编号+寄存器，触发一次受控的特权级切换"。x86_64 用 syscall 指令进入，entry_SYSCALL_64 是唯一入口。
原理 P24：系统调用约定 x86_64

• rax = 系统调用号（sys_read=0, sys_write=1, sys_open=2, ..., sys_openat=257）
• 参数：rdi, rsi, rdx, r10, r8, r9（最多6个）
• 返回值：rax（负值表示 -errno）
• 进入后切换到内核栈、保存寄存器、根据 rax 查 sys_call_table 调用目标函数。
